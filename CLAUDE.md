# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

This is a Bun workspace monorepo (`client` + `server` + `e2e` + `core`). Run everything through Bun, not `npm`/`node`.

```bash
# install (run from repo root; installs both workspaces)
bun install

# run both client (Vite, :5173) and server (Express, :3001) concurrently
bun run dev

# run a single workspace instead of both
bun run --filter client dev
bun run --filter server dev

# typecheck all three workspaces (tsc -b in client, tsc --noEmit in server and e2e)
bun run typecheck

# build (client only currently produces a build artifact)
bun run build

# lint (client only; oxlint, not eslint)
cd client && bun run lint

# add a shadcn/ui component (run from client/ — components.json lives there)
cd client && bun x shadcn@latest add <component>

# database (run from server/ — needs server/.env's DATABASE_URL set)
cd server && bun x prisma migrate dev   # apply/create migrations
cd server && bun x prisma generate      # regenerate src/generated/prisma client
cd server && bun prisma/seed.ts         # create/update the admin user from ADMIN_EMAIL/ADMIN_PASSWORD in .env

# e2e (Playwright) — one-time setup only, see e2e/README.md
bun run test:e2e:setup                  # migrate + seed the separate helpdesk_test database
bun run test:e2e                        # run Playwright (currently no spec files — pure harness scaffolding)

# client component tests (Bun's built-in test runner + React Testing Library, not Jest/Vitest)
cd client && bun test                              # run all *.test.tsx files
cd client && bun test src/pages/UsersPage.test.tsx  # run a single file
cd client && bun test --test-name-pattern <regex>   # filter by test name
cd client && bun run test:watch                     # re-run affected tests on save, for writing new tests
```

**Executing:** the four `bun test` invocations above are equivalent to `bun run test` / `bun run test:watch` (client `package.json` scripts) — either form works, prefer whichever is already in flight (e.g. leave `test:watch` running in a terminal while iterating on a new test rather than repeatedly invoking `bun test` one-off).

**Writing:** component tests live alongside the component they cover, named `<Component>.test.tsx` (e.g. `client/src/pages/UsersPage.test.tsx` — copy its structure for new ones: mock `@/lib/api`'s `apiFetch` per-test with `mock<...>()` + `.mockReturnValue(...)`/`.mockReset()` in `beforeEach`/`afterEach`, wrap the component in a fresh `new QueryClient({ defaultOptions: { queries: { retry: false } } })` + `QueryClientProvider` if it uses TanStack Query, and assert via RTL's `screen`/`within` queries plus `@testing-library/jest-dom` matchers like `toBeInTheDocument()`/`toHaveTextContent()`). Two non-obvious rules from that file to follow in new tests, both stemming from ES module import hoisting (imports resolve before any other top-level code in a module runs, regardless of source order):
- To mock a module (e.g. `@/lib/api`), call `mock.module("@/lib/api", () => ({ apiFetch: mock(...) }))` *before* a dynamic `await import("./ComponentUnderTest")` of the component — never a static `import` of the component in the same file, or the real (unmocked) module wins the race.
- Don't add new preload-time setup (e.g. another testing-library plugin) into the same file as `@happy-dom/global-registrator`'s `GlobalRegistrator.register()` call — see the `bunfig.toml`/`src/test/happydom.ts` note below for why that breaks silently.

`client/bunfig.toml` preloads two files in order — `src/test/happydom.ts` (registers `@happy-dom/global-registrator` as the global DOM) then `src/test/setup.ts` (extends `bun:test`'s `expect` with `@testing-library/jest-dom` matchers and runs RTL's `cleanup()` after each test) — **they must stay in two separate files**, not merged into one: since imports hoist, if the happy-dom registration and the `@testing-library/react` import lived in the same file, `@testing-library/react`'s (and `@testing-library/dom`'s) module-level code would evaluate before `GlobalRegistrator.register()` ever ran, and `screen`'s document-bound queries would silently break. `client/src/test/jest-dom.d.ts` is a type-only ambient module augmentation (`declare module "bun:test" { interface Matchers ... }`) needed because `@testing-library/jest-dom`'s bun-specific type augmentation file isn't reachable through its package.json `exports` map — don't delete it thinking it's dead code. The `e2e` workspace is Playwright (`@playwright/test`), a separate concern from Bun's test runner — see the Architecture section below and `e2e/README.md`.

**Testing strategy: prefer component tests, reach for e2e only when necessary.** A client component test (bun test + RTL, see above) is faster to run and cheaper to maintain than a Playwright e2e spec, so it's the default for anything a component test *can* verify — validation/error rendering, conditional UI (e.g. role-gated links/buttons), loading/empty/error states, form submission logic against a mocked `apiFetch`. Reserve e2e tests for what genuinely requires the full stack: real cross-page navigation and redirects, an actual session round-tripping through better-auth's cookie, or server-only behavior with no React component to test against (e.g. a webhook route) where the thing under test is the HTTP contract itself, not UI. When a piece of behavior could be verified either way, write the component test, not the e2e spec.

**Prune e2e coverage that a unit/component test already proves, every time — don't let it accumulate.** After writing (or reviewing) an e2e spec for a page, check each of its assertions against that page's component test suite (and its child components' suites): if a component test already exercises the same behavior against a mocked `apiFetch` — a mutation's request shape, a query-cache write, validation/error rendering, a loading/empty state — drop the e2e duplicate rather than keeping both. This includes "does it actually persist" checks for a mutation whose request/response contract a component test already covers with a mock: real persistence for a route with no dedicated HTTP-contract test is a gap worth flagging, but close it with a direct API-level e2e test in the style of `tickets-webhook.spec.ts` (`request.post/patch(...)` against the route, no UI), not by driving the same mutation through page clicks — clicking through the UI to verify a PATCH/POST body shape re-tests what the component suite already proves and only adds Playwright's slower, flakier surface on top. What's left after pruning is usually small: a page-load smoke test for real, authenticated end-to-end wiring (session cookie → route guard → live Prisma schema → rendering — the class of bug a mocked `apiFetch` structurally cannot catch, e.g. the page 500ing because `helpdesk_test` was missing a migration) plus any genuine cross-page navigation/redirect. Client-side routing driven by a `Link`/`Button` click (no full page load) belongs in a component test with `MemoryRouter`, not e2e, even though it "navigates" — reserve e2e navigation coverage for what actually requires a real browser (redirects, back/forward, a route guard's server round trip).

**Writing, extending, or fixing Playwright e2e tests: use the `e2e-test-writer` subagent, don't write specs directly.** This applies to the main session/agent handling a user request — not to the `e2e-test-writer` subagent itself once invoked: if you *are* that subagent (or any other agent that was specifically dispatched to write the specs), just do the work directly, there's no further subagent to delegate to. Otherwise, delegate any request like "write an e2e test for X" / "add Playwright coverage for Y" / "the e2e test for Z is flaky" to it (`.claude/agents/e2e-test-writer.md`) rather than editing `e2e/tests/*.spec.ts` inline yourself — it already knows the harness details (dedicated test DB/ports, seeded test admin, the bun/chromium CLI-vs-programmatic distinction, project test-style conventions) so those don't need to be re-derived or re-explained each time. If the subagent type isn't available in the current session (it was added after the session's agent registry loaded), say so rather than falling back to writing specs directly — a fresh session will pick it up.

## Architecture

**Two independent apps, not a single build.** `client` (React 19 + TypeScript + Vite) and `server` (Express 5 + TypeScript, run directly by Bun with no compile step) are separate workspaces with separate `package.json`/`tsconfig.json`. They talk over plain HTTP: the client's `auth-client.ts` hits the server via `baseURL` (see Auth below for why that's env-driven, not hardcoded), and the server has `cors({ origin: process.env.CLIENT_URL, credentials: true })` in `server/src/index.ts` (needed for the better-auth session cookie to cross origins) — kept in sync with better-auth's own `trustedOrigins`, both reading the same `CLIENT_URL` env var.

**`core` is a fourth workspace, shared between `client` and `server`, with no build step** — both consume its TypeScript source directly (`core/package.json`'s `exports` maps `"."` to `./src/index.ts`; `client`'s Vite/esbuild and `server`'s Bun runtime both resolve `.ts` sources natively, same as the rest of the monorepo). It exists specifically to hold **zod schemas that must be identical on both sides** — e.g. `core/src/schemas/user.ts`'s `createUserSchema`, used by `client/src/components/CreateUserDialog.tsx` (via `zodResolver`) for client-side form validation and by `server/src/routes/users.ts` for request-body validation on `POST /api/users`. Sharing the literal schema object (not just re-typing the same rules twice) is the point — it's what guarantees the client's inline field errors and the server's 400 response can never drift apart. **When adding a new zod schema that both `client` and `server` need to validate against the same shape, define it in `core/src/schemas/` (export both the schema and its `z.infer` type from `core/src/index.ts`) and import it from `"core"` in both workspaces — don't redeclare it separately in each.** Schemas used by only one side (e.g. `LoginPage.tsx`'s login form schema, which the server never validates against) stay local to that workspace; `core` is for the shared case only. `core/src/constants/role.ts` follows the same sharing principle for a plain (non-zod) value: it exports `Role` as a `{ admin: "admin", agent: "agent" } as const` object (mirroring the shape Prisma itself generates for enums) plus its inferred `Role` type, so the client — which has no access to `server/src/generated/prisma` (server-only, gitignored) — has a typed way to reference role values. **Never hardcode the `"admin"`/`"agent"` string literals directly in a comparison or conditional; use `Role.admin`/`Role.agent` from `"core"` instead** (see `client/src/components/Navbar.tsx`, `RequireAdmin.tsx`, and `UsersTable.tsx` for the pattern). On the server, prefer the Prisma-generated `Role` (`server/src/generated/prisma/client.ts`, re-exported enums file) for anything touching Prisma types directly (`server/src/routes/users.ts`, `server/src/middleware/requireAdmin.ts`, `server/src/lib/auth.ts`) — it's regenerated automatically from `schema.prisma`'s `enum Role` and is structurally identical to `core`'s version, so the two never drift. **Not every shared Prisma enum needs a `Role`-style runtime const object, though** — `core/src/constants/ticketStatus.ts` and `ticketCategory.ts` export `TicketStatus`/`TicketCategory` as plain string-literal union types (`"open" | "resolved" | "closed"`, etc.), not a `{ open: "open", ... } as const` object. The distinguishing factor is whether client code ever needs the enum's *values* at runtime (`Role.admin` is used in equality checks in `Navbar.tsx`/`RequireAdmin.tsx`) versus purely as a *type* for typing already-fetched data (`TicketsTable.tsx` only needs `TicketStatus`/`TicketCategory` to type its `Record<..., ...>` display-label lookups, keyed by ordinary string literals) — use a plain union type for the latter, and only reach for the `Role`-style const object when something needs to reference a member by name (`Role.admin`) rather than write the literal out. New workspace packages need a matching entry added to the root `package.json`'s `workspaces` array and a `"<name>": "workspace:*"` dependency in the consuming workspace's `package.json`, then `bun install` from the repo root to link them.

**Server is Express 5**, not Express 4 — `server/package.json` pins `express@^5.2.1`. Express 5 changed some routing/wildcard behavior and removed some Express 4 methods; don't assume Express 4 patterns from training data apply without checking. Note the auth catch-all route uses Express 5's named-wildcard syntax: `app.all("/api/auth/*splat", ...)`, not the bare `*` Express 4 pattern.

**Request-body validation in routes goes through `server/src/lib/validate.ts`'s `validateBody(schema, req, res)`**, not an inline `schema.safeParse(req.body)` block. It runs the zod parse, and on failure writes the standard `400 { error: "<zod message>" }` response itself and returns `undefined`; on success it returns the typed parsed body. Callers do `const body = validateBody(schema, req, res); if (!body) return;` before destructuring — see `server/src/routes/users.ts` (`POST /`, `PATCH /:id`) and `server/src/routes/tickets.ts` (`POST /inbound`) for the pattern. This exists specifically so the 400-response shape can't drift between routes; add any new route's validation through this helper rather than re-inlining the safeParse/400 block.

**Bun runs TypeScript directly.** `server/src/index.ts` is executed as-is by Bun (`bun src/index.ts` / `bun --watch src/index.ts`) — there's no `tsc` build step in the server's run path. `tsc --noEmit` in `server` is typecheck-only. `server/src/env.ts` is imported first (before `./lib/auth.ts`) and throws if any of `DATABASE_URL`/`BETTER_AUTH_SECRET`/`BETTER_AUTH_URL`/`CLIENT_URL` is missing, so a misconfigured env fails fast at startup instead of partially initializing (`PORT` is optional, defaults to `3001`).

**`e2e` is a third workspace, Playwright only, no spec files yet.** It runs the whole app against a separate `helpdesk_test` PostgreSQL database on dedicated ports (server `:3002`, client `:5174`) rather than the dev ports/database, so a test run can't collide with a `bun run dev` session or touch real dev data. This required one product-code change: `client/src/lib/auth-client.ts`'s `baseURL` reads `import.meta.env.VITE_SERVER_URL` (falling back to `http://localhost:3001`) instead of a hardcoded string, so Vite can point it at `:3002` during e2e runs (see `e2e/playwright.config.ts`'s `webServer.env`). `e2e/playwright.config.ts`'s `webServer` array boots both apps itself — `server` via `bun --env-file=.env.test --watch src/index.ts` (a gitignored `server/.env.test`, templated by `server/.env.test.example`), `client` via `bun run dev -- --port 5174`. Since sign-up is disabled (see below), a known test admin is seeded into `helpdesk_test` via `server/prisma/seed.ts` itself (through the `test:seed` script, env-scoped to `.env.test`) — there's no other way to get a logged-in user into that database. The one-time manual setup (creating the `helpdesk_test` database itself, since `prisma migrate deploy` won't create it) is in `e2e/README.md`.

**Auth is better-auth + Prisma + PostgreSQL, already wired end-to-end.** `server/src/lib/auth.ts` configures `betterAuth()` with a Prisma/Postgres adapter (`@prisma/adapter-pg`), email+password sign-in with sign-up disabled (agents are provisioned by an admin, not self-registered — see `prisma/seed.ts` for the bootstrap admin user), and a required `role` field (`admin` | `agent`, defaults to `agent`) added via `user.additionalFields` (`input: false`, so it can't be set/escalated through the sign-up or update-user payload). The `betterAuth()` options object is built as a separate `options` const (typed via `satisfies BetterAuthOptions`) rather than inlined, specifically so the `customSession` plugin below can be passed that same `options` value as its generic-inference argument and see the `role` field's type. Two more things are configured there: `rateLimit` (`window`/`max` plus a tighter `customRules["/sign-in/email"]`) — `enabled` is deliberately left unset so it falls back to better-auth's own default of production-only, since forcing it on in dev/e2e blocks rapid manual/automated login attempts; and a `customSession` plugin that strips the raw session `token` field out of the `/get-session` response (what the client's `useSession()` polls) — by default better-auth returns that token in the JSON body alongside the httpOnly cookie, which would let an XSS payload or any client-side logging of session state exfiltrate a valid session token. `server/src/middleware/requireAdmin.ts` (checks `auth.api.getSession(...)` + `role !== Role.admin`, 401/403 otherwise) is wired to every route in `server/src/routes/users.ts`. The Prisma client is generated into `server/src/generated/prisma` (gitignored-generated code, not hand-written — don't edit it directly; change `server/prisma/schema.prisma` and run `bun x prisma generate`/`migrate dev` instead). On the client, `client/src/lib/auth-client.ts` wraps `better-auth/react`'s `createAuthClient` with `baseURL: import.meta.env.VITE_SERVER_URL ?? "http://localhost:3001"` (env-driven so e2e can point it at the server's alternate port — see the `e2e` paragraph above); `client/src/components/RequireAuth.tsx` is a React Router layout route that redirects to `/login` when there's no session and otherwise renders the shared `Navbar` + an `<Outlet />`; `client/src/components/RequireAdmin.tsx` is a second layout route, nested inside `RequireAuth`, that redirects to `/` unless `session.user.role === Role.admin` (it assumes `RequireAuth` already handled the pending/no-session cases, so it doesn't re-check those) — like the server middleware, this is a UI-only gate, not a security boundary on its own.

**Routing is React Router 7** (`react-router-dom`), wired in `client/src/main.tsx` (`<BrowserRouter>`) and `client/src/App.tsx` (`<Routes>`). `/login` is public; `/` and `/users` are nested under the `RequireAuth` layout route and redirect unauthenticated users to `/login`; `/users` is additionally nested under `RequireAdmin`, so non-admin agents get redirected to `/`. `Navbar` only renders a link to `/users` when `user.role === Role.admin`.

**Styling is Tailwind CSS v4 + shadcn/ui**, installed directly in `client` (not just hoisted from the workspace root — `tailwindcss`/`@tailwindcss/vite` must be direct `client/package.json` deps or `shadcn`'s CLI preflight check fails to detect Tailwind). Tailwind v4 is config-file-less: theming lives in `client/src/index.css` via `@theme inline` + `:root`/`.dark` CSS custom properties, not `tailwind.config.js`. shadcn is set up with `components.json` (style: `base-nova`, base color: `neutral`, icon library: `tabler`) and generated components live in `client/src/components/ui/`; add more with `bun x shadcn@latest add <component>` from `client/`. Path alias `@/*` → `client/src/*` is configured in both `tsconfig.json`/`tsconfig.app.json` and `vite.config.ts`'s `resolve.alias`.

**Forms use react-hook-form + zod**, resolved via `@hookform/resolvers/zod` (see `client/src/pages/LoginPage.tsx` for the pattern: a zod schema, `useForm({ resolver: zodResolver(schema) })`, and `register()` spread onto shadcn `Input` components). `client/src/components/CreateUserDialog.tsx` (the "Create user" modal on `/users`) follows the same pattern, except its schema (`createUserSchema`) is imported from the shared `core` workspace rather than declared inline — see the `core` paragraph above. New forms should follow this pattern too (local schema unless the server also validates against it), rather than manual `useState`/`onChange` handling.

**AI ticket auto-resolution runs as background pg-boss jobs, in the same process as the API — it is not a separate worker to start.** When `POST /api/tickets/inbound` creates a new ticket, it responds `201` immediately and only then fires two independent, fire-and-forget jobs (`server/src/routes/tickets.ts`, `queueTicketClassification`/`queueTicketResolution`, both `.catch()`-logged so an enqueue failure can't crash the request): `classify-ticket` (`server/src/lib/classifyTicket.ts`) sets `ticket.category` via `generateObject`; `resolve-ticket` (`server/src/lib/resolveTicket.ts`) is the real "AI agent" — it sets the ticket to `processing` (assigning the `ai@helpdesk.local` user via `getAiAgentId()`, `server/src/lib/aiAgent.ts`), calls `resolveTicketFromKnowledgeBase()` (`server/src/lib/knowledgeBaseResolver.ts`, which loads `server/knowledge-base.md` and answers only from it, escalating on any of the KB's own "Escalation Rules" or low confidence), then either creates an AI `Reply` and flips the ticket to `resolved` **and actually emails the customer** via `sendTicketReply()` (`server/src/lib/email.ts`, Mailgun, with proper `Message-Id`/`In-Reply-To`/`References` threading off the ticket's/prior replies' message IDs — mirroring the human-agent reply route at `POST /:id/replies`), or resets it to `open`/unassigned with no email if the KB doesn't confidently answer it. All four AI features (classify, resolve, summarize, reply-polish) share one rate-limited free model (`server/src/lib/ai.ts`'s `openrouter/free` via `@openrouter/ai-sdk-provider`), so 429s and even outright `AI_NoObjectGeneratedError`s (the free model occasionally returns no parseable structured output) are expected, routine failure modes, not bugs — both `resolve-ticket` and `classify-ticket` queues are created with `retryLimit: 3, retryBackoff: true, retryDelay: 5` specifically so a transient AI failure gets a few backed-off retries (`resolveTicket()`'s catch block re-throws to let pg-boss retry when `job.retryCount < job.retryLimit`, from `boss.work(..., { includeMetadata: true }, ...)`, and only falls back the ticket to `open` once retries are exhausted) instead of silently mis-treating an infra failure as a legitimate "can't answer this" escalation. Both queues also set `expireInSeconds: 120` (pg-boss's own default is 900) so that if the worker process dies mid-job (a dev-server `--watch` restart, a crash, a deploy) the orphaned job is reclaimed and retried within ~2 minutes instead of leaving a ticket stuck in `processing` for 15 minutes. **`processing` is a deliberately transient, system-only status and is excluded from the ticket list by design** (`ticketListStatuses` in `core/src/constants/ticketStatus.ts`, enforced server-side at `tickets.ts`'s `GET /` via `status: query.status ?? { not: TicketStatus.processing }`) — a ticket "not showing up" almost always means it's stuck in `processing`, which (before the fixes above) could happen indefinitely; check `pgboss.job` (`state`, `retry_count`, `started_on`) for the corresponding `resolve-ticket` job before assuming it's a new bug. `server/src/lib/resolveTicket.test.ts` is the reference example for testing this kind of background-job logic: `bun:test` + `mock.module` (same pattern as client component tests, see below) mocking `./prisma.ts`/`./email.ts`/`./knowledgeBaseResolver.ts`/`./aiAgent.ts`/`./queue.ts`, importing the exported `resolveTicket(ticket, retryInfo?)` directly rather than going through pg-boss.

**Custom (non-better-auth) server API calls use axios + TanStack Query, not raw `fetch`.** `client/src/lib/api.ts` exports an `apiClient` (`axios.create({ baseURL: SERVER_URL, withCredentials: true })`, `SERVER_URL` from `import.meta.env.VITE_SERVER_URL` same as `auth-client.ts`) and an `apiFetch<T>(path, init?)` wrapper around it that normalizes axios errors into `Error(message)` from the response body's `error` field. `QueryClientProvider` is set up once in `client/src/main.tsx` wrapping the whole app. Data-fetching pages call `useQuery({ queryKey, queryFn: () => apiFetch<T>(path) })` rather than a manual `useEffect`/`useState` pair — see `client/src/pages/UsersPage.tsx` for the reference pattern (loading via `isPending`, error via the query's `error`). better-auth's own client (`authClient`/`useSession`) is unaffected by this — it keeps using better-auth's internal fetch handling, not `apiClient`.
